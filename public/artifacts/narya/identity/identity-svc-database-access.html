identity-svc Database Access

apps/shared-secrets · identity-svc-db-appidentity-svc database access

identity-svc keeps its data in its own Postgres database, identity_svc. On staging that database sits on the shared staging-postgres server, narya-postgres.staging.pmadvisors.my. The pods reach it through an in-cluster NetBird egress proxy. A laptop that is on NetBird connects to the server directly and never uses the proxy. Both use a SOPS-managed credential. This page records where the database lives, which credentials exist, and how an operator connects. It holds no passwords.

At a glance

What an operator needs to know

Its own database

identity_svc is separate from core. identity-svc owns human identity (persons, login identities, sessions, signing keys) under ADR-0119, so its tables are not in Core's schema.

One app credential

identity_svc_app_user is shared by the api, its migrate init container and the outbox relay. Every one of them reads DB_DSN from the secret's dsn key.

Reached through NetBird

Pods connect to narya-postgres-egress in the netbird namespace, not to Postgres directly. A NetworkPolicy admits only the identity-svc workloads.

Laptops skip the proxy

From DBeaver or psql on your machine, use host narya-postgres.staging.pmadvisors.my. The …svc.cluster.local name only resolves inside the cluster, so it fails with “Unknown host”.

Secrets live in SOPS

The credential is age-encrypted in infra-gitops, and its twin lives in infra-ansible. Decrypt locally when you need it. Never paste it into a document or an agent session.

Procedure

Get the staging password

Run these steps in your own terminal. You need the age key at ~/.config/sops/age/keys.txt.

  1. Update infra-gitops. Local checkouts often fall far behind, so read from origin/main.

    cd ~/projects/pma/infra-gitops && git fetch origin

  2. Decrypt the secret and print only the password. The data fields are base64.

    git show origin/main:apps/shared-secrets/staging/proxmox/office/identity-svc-db-app.sops.yaml \
  | sops -d --input-type yaml --output-type yaml /dev/stdin \
  | awk '/^  password:/{print $2}' | base64 -d; echo

    Don't run this inside an agent session. The secret's dsn, uri and pgpass keys all contain the password too, so decrypting the whole file prints it several times.

  3. Pick a route under Connect, or paste the password into the builder.

Connect

Four routes on staging

Laptop

From DBeaver or psql, over NetBird

Connect straight to the server, the same way your core connection does. Use Host narya-postgres.staging.pmadvisors.my, port 5432, database identity_svc (not postgres) and user identity_svc_app_user. The egress proxy is only for pods; its svc.cluster.local name gives “Unknown host” outside the cluster.

psql -X -h narya-postgres.staging.pmadvisors.my \
  -p 5432 -U identity_svc_app_user -d identity_svc
App user

On the Postgres host

SSH to sv3-stg-postgres, then connect through the container. You see what the service sees, row-level security included.

docker exec -it staging-postgres \
  psql -X -U identity_svc_app_user -d identity_svc
Superuser

Past row-level security

Use this for audits and counts, where RLS must not hide rows (M3-R53). Print counts, not row data.

docker exec -i staging-postgres \
  psql -X -v ON_ERROR_STOP=1 -U postgres -d identity_svc
In cluster

From an identity-svc pod

The egress NetworkPolicy refuses a generic debug pod. Only pods labelled identity-svc-api or identity-svc-outboxrelay get through, and the service image may not include psql.

kubectl -n apps exec -it deploy/identity-svc-api -- sh

  Procedure
  
Rotate a credential

  
Each secret's header names its twin. Change infra-ansible first, so Postgres accepts the new password before any pod asks for it.

  

    
    
      
  1. In infra-ansible, change staging_postgres_identity_svc_app_user_password (or …_identity_svc_import_password) in inventories/prod/internal-tools/staging-postgres/group_vars/staging_postgres.sops.yml, then apply.
    2. 
      
  2. In infra-gitops, update the matching secret under apps/shared-secrets/staging/proxmox/office/. Change every key that embeds the password: password, dsn, uri, fqdn-uri, pgpass. Merge and let ArgoCD sync.
    3. 
      
  3. Restart the identity-svc Deployments so they read the new DB_DSN.
    
        
    kubectl -n apps rollout restart deploy/identity-svc-api deploy/identity-svc-outboxrelay

  Gaps
  
Open items and caveats

  

    
Rotate
The app password appeared in an agent transcript
On 2026-09-28 the identity-svc-db-app password was decrypted inside an agent session, and its dsn and pgpass keys were printed. Rotate it by following the procedure above.

    
Access
No sanctioned in-cluster debug route
The egress policy admits only identity-svc workloads, and the service image may not include psql. From outside the cluster, use the laptop route over NetBird or the host route over SSH.

    
Pitfall
“Unknown host” from DBeaver is not an outage
On 2026-09-28, a DBeaver connection to narya-postgres-egress.netbird.svc.cluster.local failed with “Unknown host”. The proxy was fine: core's and dms-gateway's /readyz, which ping the database through it, both returned 200. The name simply doesn't exist outside the cluster. That attempt also used database postgres and user identity_svc. Use identity_svc and identity_svc_app_user.

    
Unverified
Laptop route not yet tried for identity_svc
The direct route to narya-postgres.staging.pmadvisors.my is known to work for core. infra-ansible's staging-postgres README still lists only core and dms_gateway, so if login fails with an auth or “database does not exist” error, check that the identity_svc database and role were created on that server.

    
Local
Older compose volumes lack the database
The init SQL runs only on an empty data directory. Either run make compose-down (which passes -v) and then make compose-up, or create the database by hand: docker compose exec postgres psql -U narya -d core -c 'CREATE DATABASE identity_svc;'.

    
Prod
No production overlay yet
Only staging/proxmox/office exists. Production is planned to launch with identity-svc already in place (H2).

    
Unverified
Read from Git, not from the cluster
Everything here comes from origin/main manifests. Nothing was checked against the live pods, because there was no kube context.
