Identity Outbox Relay

apps/identity-svc-outboxrelayIdentity outbox relay

A single-leader worker that moves rows from identity-svc's event_outbox table onto the RabbitMQ exchange identity.events. It exists so that an identity change and its audit event commit together or not at all. It is deployed to staging but carries no traffic yet. The first event, identity.audit.recorded, arrives in slice S4.

Purpose

Why identity-svc needs a relay

identity-svc owns human identity: persons, login identities, sessions and signing keys (ADR-0119). Core keeps accounts, roles and every authorization decision, so Core must learn about each identity change for its audit log. Publishing to RabbitMQ in the request path would let a crash between the database commit and the publish lose that record. The transactional outbox avoids that gap. The identity change and an event_outbox row commit in the same transaction, and this relay delivers the row afterwards with at-least-once guarantees.

Atomic with the change

The audit row commits with the session insert, revoke, rotate, reset, relink or bootstrap reset. If writing the row fails, the identity change fails too (ADR-0123).

At-least-once delivery

Uses publisher confirms and a mandatory publish, so an unroutable message counts as a failure. MessageId is the row id, so consumers can drop duplicates.

One active leader

pg_try_advisory_lock is taken every tick. A second replica is a standby that makes no progress: more replicas add availability, not throughput.

Failures stay recoverable

Failed rows back off exponentially. Exhausted rows are parked with next_attempt_at = infinity, never deleted, so they can be inspected and replayed.

Planned events · S4

What it will publish

The plan has one event type, identity.audit.recorded. Each identity action travels as a value of its action field; there is no separate routing key per action, and nothing else is planned for identity.events (ADR-0123 §2, E3-05, E3-44, E3-77).

Same tx: the event commits with the identity change, and if writing the event fails the change fails too. Best-effort: failed sign-ins are recorded as today, and a failure to record one does not fail the request.

Payload: a mirror of audit.Record

  • event_id: UUIDv7, becomes audit_log.id
  • occurred_at: time of the change, RFC 3339 with microseconds. A late event lands in the partition for the month the change happened.
  • action, outcome
  • actor{kind,id,label}, via
  • person, account and business-context fields
  • capability, target_type, target_id, request_id
  • optional reason, changed_fields, reference: absent for every current action

How Core records it

  • Consumed from the quorum queue core.identity.audit.recorded, dead-lettering to core.dlx
  • One audit_log row per event. A replay writes nothing: ON CONFLICT (id, occurred_at) DO NOTHING plus event_inbox
  • An event with no actor is dead-lettered and alerts, because the audit writer refuses it
  • A row reaches the audit screen seconds after the change, or later during a relay or broker outage
  • The audit screen and its filter are unchanged

Deliberately no event

  • Revocations Core instructs: account or platform-account status change, attachment detach, SuspendPersonAccounts, tenant session revocation
  • Suspension
  • "Ensure" calls: create, find, re-issue
  • In each case Core writes its own audit row in its own transaction, so an identity-side event would duplicate it (ADR-0041)

Sequence

One relay tick, step by step

The loop runs every MQ_OUTBOX_POLL_INTERVAL (1s). Each tick drains one batch of at most 100 rows. Use the arrow keys or the buttons.

Retry budget

How long before a row is parked

Delay before the next try is base × 2^attempts, capped at 1 minute (retry.go). The relay only checks on its 1s tick, so real waits round up. Staging runs the defaults.

Gaps

Open items and accepted risks

S4

No producer, message contract or consumer yet

api/asyncapi.yaml has channels: {} until E3-77 declares identity.audit.recorded. Core's quorum queue, the binding and the DLQ also land in S4. The infra-gitops change must merge and sync before the backend PR (ADR-0123).

Contract

Ten actions or eleven?

ADR-0123 and E3-44 say the event carries "exactly today's ten action names", but ADR-0122's actor_via table lists eleven, including platform_bootstrap. ADR-0123 lists only "bootstrap reset" as audited. Settle this before E3-77 fixes the action enum: the contract is unversioned and its queues retain messages, so it is hard to change later.

Order

An early row would be parked, not held

With no queue bound, a mandatory publish is returned, and the row is parked after 5 attempts (about 7.5s). That contradicts the base kustomization comment saying it "stays in the outbox". Parked rows need a manual replay.

Runbook

Runbook selector misses this pod

The runbook's kubectl commands filter on app.kubernetes.io/component=outboxrelay, but this Deployment sets only app.kubernetes.io/name. Following the runbook as written finds nothing.

H42

Broker loss inside the retention window loses audit events

Accepted for staging only. Production needs the H12 detector.

H43

Restoring only the identity DB drops unpublished rows

Accepted risk. identityimport --replace refuses to run while any row is unpublished.

Coupling

Publish timeout reuses the consumer shutdown grace

Each publish waits up to MQ_CONSUMER_SHUTDOWN_GRACE (30s). The code flags this as a coupling.
