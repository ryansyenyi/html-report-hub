Narya Identity: Modules 1, 2 and 3

Where we stand on the road to a live identity service · as of 29 Sep 2026 (backend main 5e5f037f)

The short version

The groundwork is finished. Module 1 gave us one clear idea of "who is calling". Module 2 locked down the front door and added partner integration keys, which operators can already manage from the portal. The new identity service is built and running on staging, but no traffic reaches it yet: every portal login still goes through Core. The next milestones are to switch traffic over, run the staging cut-over with a soak of at least 14 days, and then remove the old identity code from Core. Production has no deployment set up for any service, identity-svc included.

Detail by module

What we can demo, and what we can't yet

Ready to show

  • Partner integration keys, end to end. A Platform Admin issues a key in the portal, lists and revokes it, and each key shows its anchor. The key then reads devices, transactions and catalogue data (TMS-262…269, 400; web-narya #217, #230).
  • Front-door hardening, told as a security story. Malformed or smuggled tenant headers are refused. A session header or static admin key at the public edge gets a 401. Default-deny network policy is in place, and alerts fire on authorization signals. Best shown with a few curl calls and the alert rules.
  • identity-svc exists and runs on staging. Pods and the outbox relay are healthy, with signing keys and a JWKS endpoint. This is an internal API only, so show it as architecture plus kubectl, not as a user feature.

Show only with a caveat

  • Portal login. It works, but Core still serves it. Say so explicitly. Don't present it as "login now runs on identity-svc".
  • The BFF delegate key on every Core call (ADR-0139, #585, merged today). Staging must carry the delegate key on both the BFF and Core, or every portal call fails. Smoke-test staging login before the demo.
  • Integration keys on the public edge. The edge rate limits (TMS-265) must be deployed on staging before you call it from outside the cluster.

Not demo-able yet

  • Login or sessions served by identity-svc (S5/S6 not started; S5 is gated on H21).
  • Staging cut-over, the soak or rollback drills (S8b–S8g).
  • Core with its identity code removed (S9 has to wait for the cut-over plus a soak of at least 14 days).
  • Anything in production (no prod overlay exists for any service).
  • One key system for partners (TMS-268 is only a plan; legacy tenant keys still exist alongside integration keys).

Suggested narrative for stakeholders

"We rebuilt the foundations first: one identity model, a hardened front door, and partner keys, which are live on staging with a working admin UI. The new identity service is built and running on staging behind the scenes. Next we move login onto it on staging, watch it for two weeks with a tested rollback, then remove the old code from Core. Production follows once there is a production environment to deploy to."
